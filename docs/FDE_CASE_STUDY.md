# FDE 案例：公众号六图内容流水线

## 业务问题

原流程包含选题、资料提炼、文章重写、六图设计、生图、公众号上传和验收。单篇手工操作可行，但扩展到 50 篇后出现四类问题：

1. 选题容易重复，来源与结论缺少可追溯关系。
2. 生图任务数量大，失败后难判断哪些该补、哪些已完成。
3. 公众号贴图编辑器依赖真实悬停和文件选择，浏览器自动化不稳定。
4. 创建成功与回查失败之间若不保存 ID，重试可能生成重复草稿。

## FDE 方法

### 1. 先定义数据契约

每个选题绑定来源引用、单一痛点、单一承诺和一个读者交付物。每篇文章固定输出来源卡、正文和六图指令。发布清单固定为一个短标题、一段摘要和六张有序图片。

### 2. 把高风险操作放在明确审批门后

- 选题矩阵先人工审核；
- 付费生图默认 dry-run；
- 公众号写入默认 dry-run；
- 只有 `--save-drafts` 才创建草稿；
- 代码不提供正式发表或群发能力。

### 3. 用平台官方能力替换脆弱 UI 自动化

浏览器贴图编辑器需要真实 CSS hover，无法稳定批量运行。最终采用微信官方 API：

- 永久素材：`material/add_material`
- 原生图片草稿：`draft/add` + `article_type=newspic`
- 验证：`draft/get`
- 原位恢复：`draft/update`

### 4. 为失败设计恢复路径

- 图片按 SHA-256 缓存永久 MediaID；
- 每张图上传后立即持久化；
- 草稿 MediaID 在回查前持久化；
- `needs_update` 只更新同一草稿；
- 批次结果逐篇写盘；
- 最终通过独立审计读取实际产物。

## 关键故障与处理

### 40164：IP 白名单

症状：AppID/AppSecret 有效，但官方接口拒绝请求。

处理：定位当前出口 IP，指导用户在公众号后台加入白名单；不把具体 IP 写入代码或仓库。

### 中文标题保存为字面量 Unicode

症状：草稿已创建，但标题显示 `\uXXXX`。

根因：HTTP 客户端的 ASCII 转义 JSON 与公众号 newspic 接口存在兼容问题。

处理：显式发送 UTF-8 JSON；保留已有 MediaID，通过 `draft/update` 原位修正；回查同时检查标题和正文是否残留转义。

### 审批服务 503

症状：本机高权限命令审批链不可用。

处理：停止账号写入，不绕过审批；保留断点，恢复审批服务后续跑。

## 架构取舍

- 选择官方 API，而不是抓取后台私有接口：可维护、权限边界清楚。
- 选择草稿箱，而不是自动正式发表：保留人类最终审核。
- 选择文件和 JSON manifest，而不是先建数据库：便于审查、迁移和 Git 版本管理。
- 选择阶段化命令，而不是一次黑盒运行：便于产品、运营和工程共同验收。

## 可迁移价值

这套方法可迁移到小红书图文、知识库同步、课程卡片、销售内容包等流程。需要替换的是渠道适配器；选题契约、证据映射、图片任务、幂等状态和审批门可以复用。
